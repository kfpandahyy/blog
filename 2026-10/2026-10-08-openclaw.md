# OpenClaw 调研：从一小时原型到基金会，多渠道 Agent 网关成了自托管基础设施

> **TL;DR**：OpenClaw 是一个自托管的开源网关，把 WhatsApp / Telegram / 飞书 / 微信等 24+ 消息渠道接到 AI coding agent 上，单一长驻进程（Gateway）统一管渠道、会话、记忆、定时任务与多 agent 路由。它用 100 天走完 Clawdbot → Moltbot → OpenClaw 三级改名、登顶 GitHub 星标史，随后创始人加入 OpenAI、项目转基金会。选型一句话：要"在自己机器上养一个随时可聊、能动手干活的私人 agent"，它是当前事实标准；要云端免运维或企业级 SLA，它不是答案。
> **数据截至 2026-10。** 该项目迭代极快（版本号即日期），能力以 GitHub releases 与官方文档为准。

你有没有算过，自己一天在多少个聊天窗口之间切换？微信、Telegram、飞书、Slack、iMessage——人的注意力被渠道切碎，而 AI 助手却被锁在各自的网页里。2025 年 11 月，一位奥地利开发者用一小时写了个原型：把 WhatsApp 消息转发给 Claude Code CLI，再把回复发回去。四个月后，这个原型成了 GitHub 星标史上增长最快的项目，它的吉祥物 Molty 龙虾和暗号"EXFOLIATE"成了数字图腾。

它叫 OpenClaw。本文的回答方式：先给它的来龙去脉（三级改名、爆火、创始人加盟 OpenAI、基金会化），再拆架构（Gateway 单进程、渠道插件化、agent 内核可插拔、会话与记忆的工程实现），最后落到实践与风险。

一个类比贯穿全文：**OpenClaw 是 agent 时代的电话总机**。消息渠道是打进来的电话线，agent 是接线员，Gateway 是交换机——多线接入、按规则转接、通话记录存档。类比出处：官方文档自称 "multi-channel gateway for AI agents"；总机模型是本文归纳。

**一手信源声明**：本调研除公开资料外，还包含一个部署中的 OpenClaw 实例的直接观察（Linux 主机，版本 2026.4.14，跑在你正在用的这个 agent 底下）。文中"实测"处即指该实例。

## 一、定义与边界

**OpenClaw 是在你自己的机器上运行的开源网关：把一个或多个 AI coding agent 接入 24+ 消息渠道，统一管理会话、记忆、定时任务、多 agent 路由与工具执行。**（定义依据：官方文档与包描述，2026-10）

拆开看四个边界：

- **它不是聊天机器人框架**。官方定位是 "agent-native"：为带工具调用、会话、记忆、多 agent 路由的 coding agent 而生，不是为 FAQ bot 而生。
- **它不是模型**。它按模型提供方（provider）抽象接入 Claude / GPT / Gemini / Kimi / 本地模型（Ollama 等），模型可换，网关不动。
- **它不是云服务**。数据、配置、密钥都在你自己的磁盘上（`~/.openclaw/`），官方不提供托管版——这正是它的卖点也是门槛。
- **它不是单一 harness**。内置 agent 运行时之外，它还通过 ACP 协议外部接入 Claude Code、Codex 等 harness，网关层与执行层解耦。

与相近概念的区分：LangGraph 是"造 agent 的库"，OpenClaw 是"养 agent 的家"；前者给你积木，后者给你带水电的房子。本博客《Agent Harness 调研》说的 harness 是"身体"，OpenClaw 是给身体接神经末梢（渠道）和海马体（持久记忆）的那层。

## 二、何时用，何时不用

**适合用**：

- 你想在通勤路上用 WhatsApp / 微信指挥家里的电脑干活（跑脚本、查日志、发邮件）。
- 你已经有 API key，不想把对话数据交给任何托管服务。
- 你要同时服务多个渠道（个人微信 + 飞书工作群 + Telegram），不想每个渠道写一个 bot。
- 你要让多个隔离 agent（工作、私人、家庭各一个）共用一个网关，按渠道账号路由。

**不适合用**：

- 你要零运维：自托管意味着升级、备份、安全补丁都是你的事。生态日报里"升级焦虑"是高频痛点（2026-04 至 09 多期）。
- 你要多人在线协作的企业 IM 场景：它的多 agent 是"隔离"而非"协作"，delegate 架构面向的是组织代理不是团队协同。
- 你没有一台常开的机器：网关是长驻进程，笔记本电脑合盖即失联。社区流行解法是一台 Mac mini 或 VPS 常开。
- 合规要求密钥外置托管：它支持外部密钥管理（AWS KMS / HashiCorp Vault，2026.3.2 起），但机器本身仍是你的责任边界。

**核心 trade-off**：自由换责任。你拿到的是数据主权和无限定制权，交出的是运维税和安全自担。

## 四、解剖：架构与原理

**总览：一个长驻 Gateway 进程拥有全部消息面。**（官方 Gateway Architecture 文档）控制面客户端（macOS app、CLI、Web UI、自动化）通过 WebSocket 连 Gateway（默认 `127.0.0.1:18789`）；移动/桌面节点（macOS / iOS / Android / headless）同样走 WS，但以 `role: node` 声明能力；HTTP 同端口承载 Canvas（agent 可编辑的 HTML/CSS/JS 页面）与 A2UI 宿主。**一台机器一个 Gateway，它是唯一打开 WhatsApp 会话的地方**——这个"单一所有者"设计从根上避免了多端登录互踢。

### 4.1 Agent Loop：消息如何变成行动

官方对 agentic loop 的定义（docs/concepts/agent-loop）：**intake → context assembly → model inference → tool execution → streaming replies → persistence** 的完整权威路径。工程特征：每个会话内 loop **串行**执行，生命周期与流式事件对外广播。这套"单会话串行 + 事件外发"的结构，让多端（手机 app / Web / CLI）能同时围观同一次思考过程——你手机上看到的"对方正在输入"，来自同一事件流。

实测补充（2026.4.14 实例）：一次典型 turn 是——渠道消息进入 → 拼装系统提示（SOUL.md / AGENTS.md / 记忆文件）→ 模型推理 → 工具调用（read / exec / browser / message）→ 流式回复 → 会话持久化。持久化在每次工具调用后即发生，崩溃恢复不丢已完成步骤。

### 4.2 会话、压缩与上下文工程

- **会话（session）**：每条渠道对话映射到会话；会话有隔离目标（isolated / main）两种——主会话装载 MEMORY.md 等完整记忆，隔离会话（群聊、子任务）只拿最小上下文。这是上下文经济学的产品化实现。
- **压缩（compaction）**：接近上下文上限时，旧消息被摘要成 summary 让对话继续（官方定义："compacts older messages into a summary"）。压缩前系统会触发 **pre-compaction memory flush**——把要记的东西先写进文件，再腾地方。本博客《上下文与记忆工程》的"先固化再压缩"原则在这里是内置行为。
- **队列与重试（queue / retry）**：渠道消息排队进入会话，防止并发消息把 loop 打乱；模型失败按 failover 配置切换备用模型。

### 4.3 记忆：Markdown 即真相

官方记忆文档第一句话：**"OpenClaw remembers things by writing plain Markdown files... there is no hidden state."** agent 记住的唯一方式是往工作区磁盘写 Markdown——MEMORY.md、每日笔记、TOOLS.md。模型每轮醒来都是"失忆"的，靠文件系统重建自我。

这个设计与本博客《本体与知识图谱调研》的结论异曲同工：结构化知识要落盘成文件、带索引、可检索。差异在于 OpenClaw 选择了**最朴素的载体**（纯 Markdown + 语义搜索索引），而不是图谱。工程立场：先跑起来，再按痛点升级结构。该立场也内置了记忆插件接口（memory plugins 可接管压缩前 flush，2026.10.1-beta 新增）。

### 4.4 多 agent 与 delegate

- **多 agent 路由**：一个 Gateway 内跑多个**互相隔离**的 agent（各自 workspace + agentDir + 会话），入站消息通过 bindings（渠道账号 → agent）路由。隔离是硬边界：工作记忆不共享，防止上下文串味。
- **Delegate 架构**：把多 agent 从个人场景推进到组织场景——agent 以**具名代理**身份行动，"on behalf of"人类但**绝不冒充人类**，发消息、读邮件、订日程都在自己账号下进行，授权显式（文档示例：Exchange GrantSendOnBehalfTo + Graph API application access policy 限定邮箱范围）。

### 4.5 设计决策三问

1. **为什么渠道接入统一走 Gateway 单进程而不是每渠道独立 bot？** 因为要"一个号码簿"：会话、记忆、权限、审计集中一处；代价是 Gateway 成为单点——官方用 gateway lock、健康检查、原子更新（Atomic Updates，2026.9.5）缓解。
2. **为什么 agent 内核可插拔（内置 + ACP 外部 harness）？** 因为模型和 harness 迭代快于渠道；把"会思考的"和"会说话的"解耦，任一侧升级不拖垮另一侧。
3. **为什么记忆用裸 Markdown 而非数据库？** 因为可审计、可 diff、可 git、对人可读；代价是结构化查询弱——留给记忆插件和语义搜索补位。

## 五、组件模式拆解

四种使用模式，统一微结构（一句话定位 / 何时用 / 实例）：

**5.1 渠道接入：内置 + 插件**
- 一句话定位：消息渠道是网关的"耳朵"，24+ 渠道覆盖 IM 全家桶。
- 何时用：任何"想在现有聊天工具里指挥 agent"的场景。
- 实例：内置 channels（Telegram via grammY、WhatsApp via Baileys、Slack、Discord、Signal、iMessage、Matrix）+ 渠道插件（飞书、钉钉、企业微信、QQ、微信个人号、Zalo、Nostr、IRC、Twitch、Synology Chat 等）。实测：本实例通过 openclaw-weixin 渠道插件接入微信。

**5.2 会话与上下文：main vs isolated**
- 一句话定位：上下文预算的分配器。
- 何时用：私人深度对话进 main（全记忆），群聊/一次性任务进 isolated（最小上下文）。
- 实例：直接私聊 → main session（加载 MEMORY.md）；微信群 @ → isolated session（防个人记忆泄漏给群友——安全默认）。

**5.3 技能与插件：Skills 是知识，Plugins 是能力**
- 一句话定位：Skill = 按需加载的程序性知识（本博客《Agent Skill 调研》的开放格式），Plugin = 带运行时能力的渠道/工具包。
- 何时用：教 agent 新本事装 Skill；接新渠道/新工具装 Plugin。
- 实例：技能市场（社区 skills）一键安装；插件免重启热装（2026.9.5）；skill 支持 installed-skill 搜索（2026.10.1-beta）。

**5.4 定时与心跳：cron + heartbeat**
- 一句话定位：让 agent 从"被问才答"变成"到点自查"。
- 何时用：周期任务（晨报、盯盘）用 cron；不定期的主动巡检（看邮件、看日历）用 heartbeat。
- 实例：cron 交付到指定渠道（"每天 8:55 发盘前情绪"）；心跳批处理多路检查，减少 API 调用。官方文档明确二者分工：时间精确用 cron，上下文依赖近期消息用 heartbeat。

**5.5 多 agent 与 delegate**
- 一句话定位：一台网关，多个"人格"。
- 何时用：一人多角色（工作/私人），或组织内具名代理。
- 实例：bindings 把"飞书工作号"路由到工作 agent、"Telegram"路由到私人 agent；delegate 以独立账号代管高管日程但不冒充高管本人。

## 八、实践：从零到一个活的 agent

最小路径（实测，Linux，约 15 分钟）：

```bash
# 1. 装（Node 24 推荐）
npm install -g openclaw
# 2. 向导
openclaw onboard
# 3. 配模型 provider（以 Kimi 为例，也可 Claude/OpenAI/Gemini/本地 Ollama）
openclaw config set providers.kimi.apiKey <key>
# 4. 起网关
openclaw gateway start
# 5. 接渠道（如微信插件，扫码或配置后即可对话）
openclaw channels add openclaw-weixin
```

验收标准：从手机给 agent 发一条消息，它回复并能执行一条只读命令（如 `df -h` 汇报磁盘）。

安全基线六条：网关绑 127.0.0.1 不暴露公网（远程走 Tailscale）；API key 用环境变量或外部 KMS，不进配置文件；exec 提权命令开审批（/approve 流程）；渠道插件只装官方/审计过的；升级前读 changelog 并备份 `~/.openclaw/`；定期 `openclaw doctor` 体检。

进阶三件事：写 SOUL.md / AGENTS.md 定义人格与工作规则（本博客所有文章的归档流程就写在 AGENTS.md 里）；用 bindings 配多 agent 路由；用 cron + heartbeat 搭主动服务（晨报、盯盘、收件巡检）。

## 九、失败模式与坑

1. **安全事件型**：2026-02-14 认证逃逸 + 沙盒绕过影响 900+ 实例——教训是"agent 有本地全权限"本身就是攻击面。缓解：及时升级（2.15 已修）、网络隔离、最小权限运行。（安全必答：你的 agent 能 exec，它就被 prompt injection 盯上了。）
2. **升级焦虑型**：生态日报多期记录"升级后功能消失/内存暴涨/需重启 Gateway 才生效"。缓解：跟 extended-stable LTS 线而非 beta 线；升级前备份。
3. **桥接脆弱型**：WhatsApp / 个人微信等非官方协议渠道，上游一改就断（生态日报 2026-07 至 09 多次）。这是所有"寄生渠道"的结构性成本，选型时把渠道维护频率算进去。
4. **信源伪造型**：微博"官方微博"李鬼事件（2026-03）——热门开源项目的"官方账号"不可默认信任，以创始人本人渠道和 GitHub 组织为准。
5. **上下文串味型**：多 agent 隔离靠 bindings 配置，配错就把私人记忆路由进工作群。上线前用测试渠道验证路由表。
6. **单点型**：一台机器一个 Gateway，进程挂 = 全渠道失联。Cron 任务依赖网关存活，关键告警不要只走 agent 这一条路。

## 十、结论与下一步

OpenClaw 的历史给出一个清晰判断：**个人 AI 助手的默认形态正在从"网页对话框"迁移到"消息渠道 + 自托管网关"**，而这个品类的基础设施层，2026 年属于这只龙虾。它把渠道接入、会话隔离、Markdown 记忆、定时主动化这四件脏活做成了标准件，让"养 agent"从手艺人活变成装机活。

下一步该盯的三个信号：基金会治理是否持续中立（OpenAI 影响边界）；delegate/组织模式能否走出个人玩家圈；以及"爪系"生态是走向兼容标准还是碎片化内卷。

给不同读者的一句话：

- **开发者**：装一个，把你最常用的渠道接上，一周内你会离不开它——然后立刻配置安全基线，别裸奔。
- **架构师**：把 OpenClaw 当"agent 接入层"参考设计：单进程总机、会话隔离、记忆落盘、内核可插拔，这四板斧值得抄。
- **产品经理**：注意它的增长公式——亚文化图腾（龙虾）× 本地自主叙事 × 渠道即入口。2026 年的开源传播，故事和代码一样重要。

## 附录：FAQ

1. **OpenClaw 和 Claude Code 什么关系？** 没有隶属关系。OpenClaw 通过 ACP 协议把 Claude Code 等 coding agent 作为执行内核接入；反过来它也支持 GPT、Gemini、Kimi 等。名字易混（前身 Clawdbot 因此被 Anthropic 要求改名）。
2. **创始人加入 OpenAI 后项目还独立吗？** 形式上独立：项目转基金会模式运营，OpenAI 承诺支持开源。但治理独立性是社区持续观察点。
3. **能接国内渠道吗？** 能。微信（个人号插件）、飞书、钉钉、企业微信、QQ 均有插件或渠道支持，实测本实例即经微信渠道工作。注意个人号插件属非官方协议，有封号与断连风险。
4. **要多少钱？** 软件 MIT 免费；成本 = 模型 API 按量 + 一台常开机器（社区主流方案 Mac mini 或入门 VPS）。
5. **和普通微信机器人框架有什么区别？** 微信机器人框架只解决"收发消息"；OpenClaw 解决"agent 的完整生命周期"——记忆、会话、工具、定时、多 agent。渠道只是它的五分之一。
