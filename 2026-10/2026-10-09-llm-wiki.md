# LLM Wiki：Karpathy 的"知识编译器"范式，以及它与 RAG、本体、Agent 记忆的关系

> 调研对象：Andrej Karpathy 2026 年 4 月提出的 LLM Wiki 模式（idea file），及其生态实现与学术衍生。
> 本篇是[本体与知识图谱调研](./2026-10-08-ontology-knowledge-graph.md)、[DBAIOps 论文精读](./2026-10-09-dbaiops-paper.md)、[DBAIOps 代码仓考古](./2026-10-09-dbaiops-repo.md)的续篇——第 4 类"上下文与记忆工程"谱系里从轻到重的最后一块：个人级、零基础设施的知识结构化范式。

## 一句话

LLM Wiki 是 Karpathy 提出的一个设计模式（不是软件）：让 LLM 当"知识编译器"，把原始素材增量编译成一个持久、互链、持续维护的 Markdown Wiki，替代 RAG"每次查询重新发现"的做法。核心主张一句话：**知识编译一次并持续保鲜，而不是每次查询重新推导。**

## 一、问题：RAG 的"从零开始"困境

Karpathy 对主流方案的诊断：NotebookLM、ChatGPT 文件上传、大多数 RAG 系统，都是查询时从原始文档检索 chunk 拼答案——**LLM 在每个问题上从零重新发现知识，没有积累**。一个需要综合五份文档的微妙问题，它每次都要重新找到并拼合相关片段。"Nothing is built up."

他没有否定 RAG 的价值，指出的是结构性浪费：检索是运行时计算，理解是重复劳动。这个批评和 Chunk 边界的语义断裂问题（小 chunk 丢上下文、大 chunk 向量匹配模糊）是同一枚硬币的两面——两者都源于"不做持久化的中间表示"。

## 二、答案：把查询成本转移到摄入时

LLM Wiki 的做法是经典的**预计算权衡**——把理解成本从查询时挪到摄入时：

- 新素材进来时，LLM 不是"索引备查"，而是**读完全文、提炼要点、整合进已有 Wiki**：更新实体页、修订主题摘要、标注新数据与旧结论的矛盾；
- 查询时，交叉引用已经建好了，矛盾已经标过了，综合分析已经反映了你读过的全部内容——这就是原文的关键句："**The wiki is a persistent, compounding artifact.**"

他用编译器作类比，精确且可操作：

| 编译器概念 | LLM Wiki 对应 |
|---|---|
| 源代码 | `raw/` 目录的原始文档 |
| 编译产物 | `wiki/` 目录的 Markdown 页面 |
| 编译器 | LLM agent |
| 构建配置 | schema 文件（CLAUDE.md） |
| 增量编译 | 新素材只更新受影响的 Wiki 页 |
| 依赖图 | 交叉引用与反向链接 |
| Lint / 静态分析 | Wiki 健康检查 |

另一个金句定义了人机分工："**Obsidian is the IDE; the LLM is the programmer; the wiki is the codebase.**" 人负责策展素材、提问、判断意义；LLM 负责全部簿记工作（summarizing, cross-referencing, filing, bookkeeping）。"I rarely touch it directly."——Wiki 由 LLM 写，人基本只读。

## 三、架构：三层 + 三操作

### 三层

1. **raw/（原始层）**：只读、不可变，事实的唯一来源；
2. **wiki/（编译层）**：LLM 全权拥有。页面分 concepts / entities / sources / comparisons 四类，外加两个特殊文件（见下）；
3. **schema（CLAUDE.md / AGENTS.md）**：告诉 LLM 结构、命名规范、页面模板、工作流——**这是把通用 LLM 变成"守纪律的 Wiki 维护者"的关键配置**，人与 LLM 在使用中共同演化它。

### 三操作

- **Ingest（摄入）**：单素材可触发 10-15 个页面的级联更新；Karpathy 偏好逐个摄入、全程参与（读摘要、查更新、引导侧重点），并把工作流写回 schema；
- **Query（查询）**：LLM 先读 `index.md` 定位相关页，再钻取合成答案，带 `[[wikilink]]` 引用。**关键设计：好答案存回 Wiki 成为新页面**——探索的产物和摄入的素材一样复利积累，不消失在聊天记录里；
- **Lint（体检）**：定期查矛盾页、过时声明、孤儿页（无入链）、被提及但没建页的重要概念、缺失交叉引用、可用搜索填补的数据缺口。

### 两个特殊文件

- **index.md**（内容目录）：每页一行摘要，按类别组织，每次摄入更新。LLM 查询时先读它——在中等规模（约 100 个来源、数百页）实测"效果好得惊人"，**绕过了 embedding RAG 基础设施**；
- **log.md**（操作日志）：只追加的时间线。每条以统一前缀开头（如 `## [2026-04-02] ingest | Article Title`），就能用 `grep` 解析。

## 四、为什么成立：维护成本趋零

Karpathy 的解释直击知识库死亡的根本原因：建知识库三步——收集（容易）、组织（难）、维护（规模上不可能）。人类放弃 Wiki 不是因为读不动、想不清，而是**簿记负担增长快于价值增长**。LLM 不会厌倦、不会忘记更新交叉引用、能一次改 15 个文件——维护成本趋零，Wiki 因此活得住。

他还把谱系上溯到 1945 年 Vannevar Bush 的 Memex：个人策展、文档间"联想小径"比文档本身更有价值的知识库愿景。Bush 当年解不了的问题是"谁来维护"——LLM 解了这最后一块。

## 五、生态：一个 idea file 催生的赛道

原文刻意保持抽象（"描述模式而非实现"），社区在几周内长出完整生态。几个有据可查的节点：

- **nashsu/llm_wiki**（GitHub 200 验证）：Tauri 跨平台桌面应用，报道口径 5 个月冲到 1.91 万星——研究/阅读/个人成长/商业模板化，内置本地 HTTP API（127.0.0.1:19828，token 保护）与 MCP Server，外部 Agent 默认只读接入；
- **Astro-Han/karpathy-llm-wiki**：Agent Skills 标准实现（社区活跃口径）；
- **llm-wiki-compiler**：Claude Code 插件，383 个 Markdown 文件实测 token 消耗降 84%（47K→7.7K）——把"查询读全库"变成"读索引+目标页"的直接收益；
- **qmd**（Tobi Lütke）：本地 Markdown 搜索引擎，BM25+向量混合检索+LLM 重排，CLI+MCP 双接口，Karpathy 点名的可选件；
- **awesome-llm-knowledge-bases**：收录 80+ 工具的清单；
- 工业侧：LinkedIn 的 CAPT 上下文知识库（1000+ 工程师，初始分诊时间降约 70%）走的同思路。

学术侧已开始把这个模式当默认参照系：WFM（Wiki Foundation Model，arXiv 2609.18182）直接把 LLM Wiki 称为 "agent-native knowledge representation" 和 "leading knowledge substrate"；多智能体知识溯源框架（arXiv 2607.24117）将其定义为系统类动机并研究声明级信任链。一个 Gist 半年内从推文变成论文的背景板，传播速度本身说明问题真实存在。

## 六、批判性解读

1. **本质是古老的预计算权衡，不是新原理。** 物化视图、增量编译、构建缓存——"把运行时成本挪到构建时"贯穿计算机科学史。LLM Wiki 的贡献是把它翻译到知识管理语境并给出可复制的模式文件。读它时不必神化，用它时不必从零发明。
2. **可信度缺口是最大暗面。** Karpathy 说"I rarely touch it directly"——无人背书的 LLM 写作会**复利错误**（compounding 的不只是知识）。Query 产物存回 Wiki 更危险：LLM 自己生成的答案变成未来检索的"事实依据"，形成自引用循环。学术场景被公开批评失效（引文纪律、一手文献要求），根源在此。DBAIOps 的反面——知识 AES 加密、DBA 审核入库——是重治理极端；LLM Wiki 是无治理极端。企业场景的答案在中间：入库分级 + 置信度字段 + 人工闸门。
3. **与本体篇是两种知识哲学。** 本体工程自上而下：先设计 schema 再灌数据；LLM Wiki 自下而上：schema 只是行为规约，知识结构由摄入过程涌现。前者保一致性、成本高；后者保活性、失控风险高。DBAIOps 走了折中（轻本体+LLM 抽取+人工校验），这是目前工业界唯一被验证的全流程。
4. **规模断言要当真。** 原文自己给的边界是"约 100 来源、数百页"。超出后 index.md 导航失效，还是要回到搜索（qmd）——那时和 RAG 的界限开始模糊。决策框架（规模、变更频率、结构化程度、工程能力四维）比站队有用。
5. **和你已经在做的事情。** 这个博客仓库本身就是手工版编译型知识库：按月目录是 `log.md` 的等价物，README 总览表是 `index.md` 的等价物，参考资料验证纪律是人工 Lint，九大类分类体系是人工 schema。LLM Wiki 模式的价值正在于把这套你已验证有效的流程自动化——这验证了模式，也说明迁移成本低。
6. **和 Agent 记忆的关系。** 它是外部记忆系统的 Markdown 实现：与 Mem0/Zep 等 agent memory 同赛道，但把"人可读可审计"放在"机器可检索"之前。对需要向人交付知识资产的场景（研究、尽调、团队 Wiki），这是正确排序。

## 七、对建设者的迁移清单

- **先跑最小形态**：一个目录 + Claude Code + Gist 内容，当天可验证；不要先建工具链；
- **schema 是核心资产**：花最多时间迭代 CLAUDE.md，把它当"知识库的 CLAUDE.md 工程"做；
- **index + log 两个文件纪律**：命名、前缀、可 grep，是最便宜的"机器可解析"投资；
- **Query 存回要加闸门**：区分"素材页"与"推断页"（frontmatter 加 `type: synthesis`），Lint 时对推断页降权重查；
- ** confidence 字段进 frontmatter**：让后续 agent 知道哪些页可信、哪些待复核；
- **规模预判**：100 来源以内享受零基础设施红利，逼近上限就引入 qmd 类混合搜索，别硬撑纯 index。
