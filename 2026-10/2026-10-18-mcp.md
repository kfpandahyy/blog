# MCP 调研：一个 18 个月大的协议，为什么把有状态握手整个删掉了

> **TL;DR**：MCP（Model Context Protocol）是 Anthropic 2024-11 开源的"模型↔工具/数据"互操作协议，现由 Linux 基金会 Agentic AI 基金会托管；2026-07-28 版完成了一次罕见的自我重写——砍掉 initialize 握手和会话状态，转为无状态核心 + per-request 版本协商 + header 路由，同时废弃 Roots/Sampling/Logging 三个原语；Tier 1 SDK 月下载近 5 亿，AWS、微软、谷歌、Cloudflare 均已站队。选型一句话：agent 要接外部工具，MCP 已是事实标准，但协议级安全（工具描述信任、跨服务器污染）至今无内建答案，生产接入必须叠加自己的防护层。
> **数据截至 2026-10-18。** 协议以官方规范（2026-07-28 版）与官方博客为准，安全争议部分引用第三方研究。

---

几乎每个 AI 应用都死在同一件事上：模型是通用的，数据和工具是私有的，中间的连接层是手糊的。MCP 把这件事标准化了——它定义的不是又一个 function calling 格式，而是一个跨进程、跨网络、跨厂商的上下文交换协议：任何客户端按 JSON-RPC 2.0 说话，就能接上任何服务器暴露的工具、资源和提示模板。

本文的路线：先界定 MCP 是什么不是什么，再给 18 个月的演进脉络，重点解剖 2026-07-28 版"无状态化"这次重写，然后看生态与安全争议，最后给选型判断和动手路径。

一句话心智模型：**MCP 想成为 agent 时代的 LSP（Language Server Protocol）——它不规定模型怎么思考，只规定工具和数据怎么被看见。**

---

## 一、定义与边界

**一句话定义**：MCP 是一个开放协议，用 JSON-RPC 2.0 在 LLM 应用（host/client）与外部能力提供方（server）之间交换上下文——工具、资源、提示模板。

**最小实例**：一个加法工具的 `tools/call` 请求（2026-07-28 版）：

```json
{
  "jsonrpc": "2.0", "id": 3, "method": "tools/call",
  "params": {
    "name": "weather_current",
    "arguments": {"location": "Xi'an", "units": "metric"},
    "_meta": {
      "io.modelcontextprotocol/protocolVersion": "2026-07-28",
      "io.modelcontextprotocol/clientInfo": {"name": "demo", "version": "1.0"}
    }
  }
}
```

**MCP 是**：传输层无关（stdio / Streamable HTTP）、能力可协商、原语动态可发现、有正式扩展机制的互操作标准。
**MCP 不是**：不是 agent 编排框架（不管任务规划），不是多 agent 通信协议（那是 A2A 的位置），不是 API 描述规范（OpenAPI 描述接口，MCP 在运行时交换调用与上下文）。

**相邻概念辨析**：

| 相邻概念 | 一句话区分 |
|---|---|
| Function calling | 模型厂商私有的单次调用机制；MCP 是跨进程的互操作协议，一个 MCP server 可被任意客户端复用 |
| OpenAPI | 静态描述 REST 接口；MCP 是运行时上下文交换，server 常把 OpenAPI 后端包装成 MCP 暴露 |
| A2A（Agent2Agent） | 管 agent 与 agent 对话；MCP 管 agent（模型）与工具/数据对话，两者互补且都进了 Linux 基金会 |
| LSP | MCP 官方自述的灵感来源：LSP 标准化"编辑器↔语言服务"，MCP 标准化"模型应用↔上下文服务" |

## 二、何时用 MCP，何时不用

**适合**：
- 给模型接一组可复用的企业工具/数据源，且希望这份集成在 Claude Code、Cursor、VS Code、自研 agent 间通用。
- 工具能力需要动态发现（`tools/list`）和实时变更通知（订阅）。
- 需要把"上下文提供方"和"模型应用方"交给不同团队/厂商维护。

**不适合**：
- 单机单进程内部调用：直接函数调用比走 JSON-RPC 省一个数量级的开销。
- 超低延迟路径：协议往返 + 内容协商有成本，热路径应直连。
- 强事务多步工作流：MCP 提供工具调用，不提供跨工具的 saga/事务语义，编排要自己搭。
- 当前阶段把第三方陌生 server 直接接进生产 agent：安全模型尚未闭环（见第六章）。

判断：MCP 的迭代速度在协议史上罕见——18 个月三个正式版本，且最新版敢于做破坏性重写（废弃 12 个月窗口内移除），说明背后生产反馈的压力真实存在。这不是缺点，是协议正在长成大基础设施的信号。

## 四、解剖：2026-07-28 版的心脏

### 4.1 架构分层

MCP 分两层：

```
┌─ 数据层（内层）──────────────────────────────┐
│ JSON-RPC 2.0 消息；版本/能力协商；原语        │
│ server 原语：Tools / Resources / Prompts      │
│ client 原语：Elicitation                      │
│ 扩展：Tasks / Skills over MCP / MCP Apps / EMA │
└──────────────────────────────────────────────┘
┌─ 传输层（外层）──────────────────────────────┐
│ stdio（本地进程） / Streamable HTTP（远程）    │
│ HTTP 侧：Mcp-Method、Mcp-Name 路由头          │
└──────────────────────────────────────────────┘
```

### 4.2 无状态化：这次重写删掉了什么

2026-07-28 版最硬的变化：**协议核心从"有状态双向连接"改为"无状态请求/响应"**。

- **删除** `initialize`/`initialized` 握手和 `Mcp-Session-Id` 头。每个请求在 `_meta` 里自带协议版本、客户端身份、能力声明；服务端按请求独立处理。
- **新增** 可选的 `server/discover` 强制 RPC：一次请求拿回服务端支持的所有版本、能力和身份。想提前协商就用它，不想就直接发请求、遇版本错误再降级。
- **后果**：任何请求可以落到负载均衡器后面的任意实例，不需要共享会话存储——这是远程 MCP server 规模化部署的解锁条件，也是 AWS Bedrock AgentCore、Cloudflare Workers 能在 day zero 支持它的原因。
- **状态去哪了**：协议不禁止服务端有状态，但要求"显式句柄"——从工具调用里铸一个 handle，让模型在后续调用里作为参数传回。设计判断很明确：**藏在传输层的状态是运维事故，摆在模型面前的状态是可审计的上下文**。

### 4.3 Multi Round-Trip Requests（MRTR）

旧版里，服务端想向用户要一个确认（elicitation）、想请求一次模型补全（sampling），需要常开双向流。新版用 MRTR 重造：服务端返回 `resultType: "input_required"` 加上待回答的请求清单，客户端把答案附在重试的 `inputResponses` 里再次发起原调用。一次往返模式替换了常驻连接，与无状态核心自洽。MRTR 同时是 Elicitation 的载体——Supabase 用它在删除数据类操作前向用户确认成本，是教科书用法。

### 4.4 为网关而生的细节

- `Mcp-Method` / `Mcp-Name` 头：Streamable HTTP 下每个请求必带，网关、限流器、WAF 可以在不解 JSON body 的情况下路由与计费。
- 列表可缓存：`tools/list`、`resources/list` 等响应带 `ttlMs` 与 `cacheScope`，客户端可缓存工具目录，重连后 prompt 缓存保持稳定。
- 授权加固：授权服务器按 RFC 9207 返回 `iss`、客户端必须校验（堵 mix-up 漏洞）；DCR（动态客户端注册）正式废弃，转向 CIMD（客户端元数据文档）；凭据绑定到签发者不可跨服务器复用。

### 4.5 扩展框架与废弃清单

扩展正式入册、双方协商后启用。首批：**Tasks**（长任务 durable handle，`tasks/get` 轮询 + `tasks/update`，由 AWS 贡献）、**Skills over MCP**（结构化技能指令经 MCP 发现与消费）、**MCP Apps**（对话内渲染交互 UI）、**Enterprise Managed Authorization**（企业托管授权）。

同版废弃（12 个月窗口，新实现不得使用）：**Roots**、**Sampling**、**Logging**；旧 HTTP+SSE 传输正式废弃。判读：Roots 和 Sampling 本是"服务端反过来请求客户端"的两个原语，MRTR + Elicitation 上位后它们失去存在理由——协议在主动收敛自己的表面积。

### 4.6 安全模型：它说了什么，没说什么

规范安全章节的原则是对的：用户必须显式同意数据访问和工具调用；工具描述应视为不可信输入（除非来自可信 server）；host 不得未经同意把资源数据外传。

但它**没有解决**的问题同样明确，见第六章的第三方研究。

## 五、原语拆解与使用模式

**Tools**：模型可执行的函数。每个工具有 `name`、`title`、`description`、`inputSchema`（JSON Schema）。工具列表是动态的，服务端可通过订阅通知变更。
**Resources**：上下文数据（文件、记录、API 响应），URI 寻址，`resources/read` 读取。适合"模型开工前要先看的背景"。
**Prompts**：复用的提示模板，服务端预置好的工作流入口。
**Elicitation**（client 侧）：服务端中途向用户要信息/确认的唯一推荐通道；走 MRTR，不需要常驻流。

常见模式：把 MCP server 当作**窄接口适配器**——后端是已有的 REST/DB/内部系统，server 只暴露精选工具 + schema 化资源，让模型看到的表面积最小。反模式：把整个数据库裸暴露成动态资源列表（schema 噪声会烧 token 并诱发误用），以及给工具写散文式 description（模型选工具全靠它，写错就是故障源）。

## 六、生态格局与安全争议

**生态**：Tier 1 SDK（TypeScript / Python / Go / C#）已同步 2026-07-28，Rust SDK beta；官方口径 Tier 1 SDK 合计月下载近 5 亿，TS 与 Python SDK 各破 10 亿总下载。发布日站台名单：AWS（Bedrock AgentCore，Tasks 扩展贡献者）、微软（Foundry）、谷歌云、Cloudflare、Figma、Sentry、Linear、Netlify、Supabase；Honeycomb 披露近 20% 月交互查询已由 agent 发起。治理侧：Linux 基金会托管，十余个工作组（Agents、Filesystems、Registry、Security、Tool Annotations、Skills over MCP 等）+ SEP 流程运转，比多数 IETF 外的年轻协议成熟得快。

**安全争议**（Invariant Labs，2025-04，第三方研究）：

- **工具投毒攻击（TPA）**：恶意指令藏在工具 description 里——用户看到的 UI 是"加法工具"，模型读到的是"先读 `~/.ssh/id_rsa` 塞进 sidenote 参数"。实验在 Cursor 上成功泄露 SSH 私钥和 MCP 配置。
- **Rug pull**：server 在用户批准工具后修改 description——初始信任无意义。
- **跨服务器 shadowing**：多 server 同连时，恶意 server 的 description 可以篡改模型对可信 server 工具的行为（实验里把邮件全部抄送攻击者）。

该团队随后发布扫描器 MCP-Scan。这些攻击利用的不是实现 bug，而是协议安全模型的真空：**工具描述被默认为可信，而它是模型上下文的一部分——上下文即提示注入面**。官方规范的回应是把"描述不可信"写进原则，但协议层面至今没有签名、校验或隔离机制。接入第三方 server 的生产系统，防护要靠客户端侧：描述全量展示、版本 pin + 哈希校验、跨 server 数据流隔离、敏感操作强制 Elicitation 确认。

## 七、对比评估与选型

| 维度 | MCP | 裸 function calling | A2A | 直接 REST 集成 |
|---|---|---|---|---|
| 厂商中立性 | 高（LF 托管） | 无（各家私有） | 高 | 视 API 而定 |
| 客户端复用 | 一次接入处处可用 | 绑定模型厂 | agent 间 | 每对一写 |
| 动态发现/订阅 | 有 | 无 | 部分 | 无 |
| 规模化部署 | 无状态后可 | 不适用 | 早期 | 成熟 |
| 安全内建 | 原则级，机制缺 | 同左 | 同左 | 成熟实践 |

**决策树**：工具要在多个模型客户端间复用 → MCP，几乎无悬念；单一自研 agent + 单一模型 → function calling 直连成本更低；agent 与 agent 协作 → MCP + A2A 组合；强合规场景 → 可以自建 MCP server 包装内网系统，但按第六章防护清单执行。

## 八、动手路径

1. **十分钟跑通**：用 TypeScript/Python SDK 写 stdio server，FastMCP（Python）一个装饰器起步；用官方 Inspector 本地调试。
2. **接进客户端**：Claude Code / Cursor / VS Code 的 MCP 配置指向本地命令即可。
3. **走向生产**：换 Streamable HTTP 传输，前置网关按 `Mcp-Method`/`Mcp-Name` 做路由与限流；远程 server 走 OAuth（注意 CIMD 是现行推荐）；工具描述按"写给模型的接口文档"标准撰写并纳入 code review。
4. **发布分发**：通过 Registry 的 `mcp-publisher` CLI 发布（namespace 与 GitHub 账号/域名绑定做所有权校验）。

## 附录

**A. 协议版本速查**：2025-03-26（首版）→ 2025-06-18（Streamable HTTP）→ 2025-11-25（有状态峰值版）→ 2026-07-28（无状态核心，现行）。版本号即"最后不兼容变更日期"，兼容更新不改号。

**B. 废弃与替代**：Roots→显式参数；Sampling→直连 LLM API；Logging→stderr/OTel；HTTP+SSE→Streamable HTTP；DCR→CIMD。废弃窗口 ≥12 个月。

**C. 已被实验证实的攻击面**：工具投毒、rug pull、跨服务器 shadowing（2025-04 Invariant Labs）；对应工具 MCP-Scan。
