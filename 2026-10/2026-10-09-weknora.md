# WeKnora：腾讯把"RAG 查询、Agent 干活、Wiki 沉淀"缝进同一个知识库

> 仓库：github.com/Tencent/WeKnora（Go，MIT，32.7k stars，最新 v0.8.2，2026-09-24 发布，提交活跃到当天）。
> 本篇是第 4 类谱系的第四篇：[本体](./2026-10-08-ontology-knowledge-graph.md)讲知识怎么被表示，[DBAIOps](./2026-10-09-dbaiops-paper.md)讲垂直领域怎么建图谱，[LLM Wiki](./2026-10-09-llm-wiki.md)讲个人级知识编译范式。WeKnora 是这条谱系的企业级终点：它把上篇"RAG vs Wiki 之争"直接产品化了——答案是"不选边，三层共存"。

## 一句话

WeKnora 是腾讯微信事业群（WXG）开源的企业级 LLM 知识平台：**同一套知识库上并行跑三种消费方式**——RAG 负责查、ReAct Agent 负责干活、Wiki Mode 负责沉淀。它回答了一个下午刚讨论过的问题：LLM Wiki 和企业 RAG 不是替代关系，是同一资产上的分工。

## 一、出身与数据

- 出身：微信对话开放平台（chatbot.weixin.qq.com）的核心技术框架开源，WXG 团队维护，官方文档站挂在 weixin.qq.com 域名下；
- 规模：32,764 stars / 4,362 forks / 588 open issues（GitHub API 实测），主语言 Go，2025-07 建仓库，近一年从 v0.2 迭代到 v0.8.2，push 活跃到当天；
- 协议：MIT（README badge 明示；GitHub API 的 NOASSERTION 是许可证检测的误报，LICENSE 头部为腾讯通告格式）；
- 部署：`docker compose up -d` 一把起，4C8G 起步；另有 Lite 单二进制（SQLite + 内存队列）、Helm、桌面版。

## 二、核心设计：三模式一库

官方一句话定义了整个设计："Use RAG to look things up, the agent for multi-step tasks, and the wiki to organize knowledge. All three work on the same knowledge bases."

| 模式 | 干什么 | 机制 |
|---|---|---|
| Quick Q&A | 事实查询 | BM25 + 向量混合检索 → rerank → 带引用回答 |
| Agent | 多步任务 | ReAct 循环，工具箱含知识检索、联网搜索、MCP 工具（含 OAuth）、技能沙箱、本地浏览器、记忆召回 |
| Wiki | 知识沉淀 | Agent 把原始文档蒸馏成互链 Markdown 页面 + 可视化知识图谱，页面可浏览器内编辑、行级 diff、一键回滚 |

这是和 Dify/RAGFlow 类平台的分水岭：那些是"RAG + 工作流"，WeKnora 把**知识沉淀**提到与查询、推理并列的第三极——正是 Karpathy LLM Wiki 模式的企业化，但补上了个人范式缺的所有企业设施。

## 三、架构拆解：五层各管一段

一手 README 加第三方架构拆解可还原出清晰的五层：

| 层 | 组件 | 职责 |
|---|---|---|
| 入口 | Vue3 Web、CLI/Go SDK、MCP client、IM 渠道、embed widget | 用户和集成进来，不直接碰库 |
| 控制面 | Go app（Gin，约 360 REST 端点）、SSE、Asynq worker | 认证、RBAC、会话、模型/工具协调 |
| 文档边界 | Python docreader（gRPC，独立服务） | anydoc 进程内解析 25+ 格式，自适应三级分块、父子分块、VLM 图片描述、ASR |
| 证据面 | PostgreSQL + ParadeDB（BM25）+ pgvector + reranker | 知识存储与混合检索；可挂 Milvus/Qdrant/Doris/Tencent VectorDB 等 7 种向量库 |
| 执行面 | ReAct Agent、MCP Server、Web Search、沙箱技能、长期记忆 | 多步动作，在证据与策略边界内运行 |
| 管控观测 | JWT/API key/OIDC、审计、Redis、Langfuse OTLP + W3C traceparent | 身份、限流、任务、追踪 |

关键设计判断：**知识数据面和 Agent 动作面分离，但共享控制面**。文档解析和 Agent 执行是两种完全不同负载，却共享租户、权限、模型与 trace 上下文——解析风暴不会冲垮问答路径（任务队列做缓冲）。

## 四、四个值得抄的工程决策

### 4.1 chunk 是一等公民，不是黑盒

多数 RAG 把向量 chunk 当不可变中间产物，错了只能重灌。WeKnora 让检索块变成可治理数据：UI 里直接编辑 chunk、和上一版 diff、一键回滚，改完自动重建索引；文件夹上传保留目录树。这回答了 LLM Wiki 篇的最大暗面——**可信度缺口**：人不是只能读 LLM 写的 wiki，还能修订检索层的事实底座，且每次修订有版本史。

### 4.2 Agent 运行时控制：steer / fork / rewind

v0.8.2 把对话从"一问一答"升级成可操纵的运行时：进行中追加要求（steer）、从历史任意问题分叉（fork）、借沙箱检查点原地回溯（rewind）、按会话选推理强度。加上会话持久的沙箱（Docker/E2B/Cube，侧边带终端和图形桌面）和 BrowserSkill 扩展驱动用户本机 Chrome/Edge（登录和验证码人工接管）——这套组合是"agent 工程"议题在企业产品里的完整落地。

### 4.3 多租户下的延迟与成本治理

任务队列仪表盘 + 分阶段 worker 池 + **按模型并发限速**：高峰时异步任务（解析、wiki 蒸馏）排队，同步问答优先；LLM API 配额按模型隔离。配套上下文压缩和 provider prompt-cache 标记压 token 负载。这是把"Day 2 运维 nightmare"当一等问题解决的架构——大多数开源 RAG 项目到 P99 尾延迟爆炸时才想起这回事。

### 4.4 可观测性用对了标准

Langfuse OTLP/OTel tracing + W3C traceparent 传播：一次提问触发 web 搜索 + 库检索 + 沙箱执行时，单一 trace ID 贯穿整个执行图。分布式 agentic 系统里这是刚需而非锦上添花。

## 五、谱系定位：LLM Wiki 之争的企业级答案

把四篇连起来看，知识结构化了四个层次：

- **本体篇**：知识自上而下 schema 优先，保一致性，贵；
- **DBAIOps**：垂直领域重图谱构建，DBA 治理入库，重；
- **LLM Wiki**：个人级零设施，自下而上涌现，活性高但无人背书；
- **WeKnora**：把查询（RAG）、推理（Agent）、沉淀（Wiki）统一在一份受治理的知识资产上——LLM Wiki 缺的企业设施（RBAC、审计、chunk 修订、追踪、并发治理）全部补齐，RAG 也没有被抛弃而是降为三极之一。

上篇批判 LLM Wiki 时说"企业场景的答案在中间：入库分级 + 置信度 + 人工闸门"。WeKnora 就是中间态的产品化实证：人工闸门落在 chunk 编辑/diff/回滚，置信度落在记忆确认流（profile/preference/fact 自动提取但**须用户确认才落库**——防记忆污染），分级落在 RBAC 四角色与 scoped API key。

## 六、批判性解读

1. **"三模式一库"的张力被设计宣言掩盖**。RAG 检索和 wiki 蒸馏对 chunk 的需求不同：前者要小而语义完整，后者要保留叙事结构供蒸馏。共享同一套分块产物是否两头妥协，官方材料没有给对照证据。GraphRAG（Neo4j）更是可选 profile——图谱深度远不及 DBAIOps 那种 30 万边的工业构建，wiki 的知识图谱是轻量级的。
2. **架构仍在动荡**。半年 v0.2→v0.8.2 的代价是破坏性变更：Neo4j 对话记忆依赖被整体移除改自研记忆；v0.8.0 移除了 Local host-process 沙箱后端；Python 版 MCP Server 被弃用改 Go 内置。588 个 open issues 是热度也是债。企业采用要钉版本，跟 trunk 有升级风险。
3. **安全的交付质感**。部署文档自己承认：沙箱命令以 root 运行、Docker 沙箱需挂 docker.sock、建议内网部署别暴露公网。功能优先、边界后置——和 DBAIOps 代码仓一脉相承的国内 to-B 风格，采用时安全面要自己做一层。
4. **生态位逻辑要读懂**。MIT + WXG 背书 + 微信渠道全家桶（企业微信、QQBot、Lark、云之家）是生态位武器：开源的是引擎，绑定的是腾讯系入口。它抢的不是 Dify 的工作流用户，是"企业内部知识库 + IM 问答"这个微信生态位。脱离微信渠道看，差异化主要在 Wiki Mode 和 chunk 治理。
5. ** Wiki 的自维护承诺需打折**。v0.5.2 宣称 wiki ingest 撑到 4 万文档 KB（靠任务队列 + DLQ），但"源文档变更→相关 wiki 页与图谱动态更新"的级联质量没有公开评测。这正是 LLM Wiki 批判里"错误复利"问题的企业放大版——量更大、更没人逐页看。

## 七、对建设者的迁移清单

- **三极分工的架构隐喻直接可用**：任何知识系统先问"查、干活、沉淀"三极各自落在哪个组件上，别让一个 RAG 链路全包；
- **chunk 可编辑 + 自动重建索引**是最低成本的"人在回路"实现，比 wiki 页审核便宜一个量级；
- **按模型并发限速**是 LLM 网关都该有的能力，照抄 worker 池 + per-model governor 模式；
- **trace ID 贯穿 agent 执行图**用 W3C traceparent + Langfuse 即可拼装，别自研；
- **记忆落库前用户确认**这个交互细节值得单独抄：自动提取 + 显式确认 = 防污染的最小方案；
- **渠道即集成**：把知识库能力以 MCP Server 形式反向暴露给 Cursor/Claude（per-workspace 端点、独立 token、按工具授权），是比做前端更聪明的生态位打法。
