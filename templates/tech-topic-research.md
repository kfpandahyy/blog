# 技术点调研模板 v3（对象：概念 / 协议 / 机制）

> v3 章节结构依据三篇业界标杆实测（2026-10 抓取原文目录）：
> - Anthropic《Equipping agents for the real world with Agent Skills》(2025-10)
> - Anthropic《Building Effective Agents》(2024-12 及其后续修订)
> - AWS Database Blog《Supercharging AWS database development with AWS MCP servers》(2025-06)
> v2 → v3 主要变化：新增"何时用何时不用"独立章（标杆均放在定义之后）；开篇四段式 + 类比；正文按组件统一微结构拆解；结尾"结论与下一步"；附录承载长尾。

## 标题 + TL;DR
- 标题断言式：`《XXX 调研：一句可争论的判断》`。
- TL;DR 三句：是什么 / 为什么此刻重要（带日期）/ 读者该做什么。

## 开篇（四段式，三篇标杆完全一致的pattern）
1. **钩子**：行业观察或真实痛点场景（"过去我们接触几十支团队，最成功的都不是用复杂框架"）。
2. **论点**：本文核心判断一句话。
3. **路线图**："本文解释 X、演示 Y、分享 Z"——让读者 10 秒知道能带走什么。
4. **类比**：一个好类比顶三段定义（Skill = 给新员工的入职手册；MCP = USB-C 接口）。

## 一、定义与边界
- 先贴最小真实实例（完整文件/命令/配置），再抽象定义——举例即定义。
- is / is-not 边界区分放在最前面（Anthropic 开篇即区分 workflows vs agents）。
- 与相邻概念辨析表。

## 二、何时用，何时不用（诚实章，紧跟定义）
- 这个技术的适用条件 + 不适用条件，各至少 3 条。
- 说清 trade-off（延迟 / 成本 / 复杂度换什么）。
- "很多场景下，更简单的方案就够了"——标杆文章敢这么写，可信度反而高。

## 三、演进脉络
- 时间线图（节点 + 日期 + 推动者 + 为什么发生）。
- 点出当时存在的备选路线，为什么胜出的是这条。

## 四、解剖：架构与原理（心脏章节，≥30% 篇幅）
- 用一个真实例子贯穿全文 walk-through（标杆做法：拿 PDF skill 一个实例从文件结构讲到触发流程）。
- 核心机制逐个讲，配流程图 / 状态图。
- 至少 3 个关键设计决策：为什么这样而不是那样。

## 五、组件 / 模式拆解（如该技术有多个组成模式）
- 每个组件用统一微结构（Building Effective Agents 的 workflow 节就是这个模板）：
  - 小节标题 = 组件名
  - 一张图
  - **何时用**（一段）
  - **示例**（2-3 个真实场景）
  - 一段注意点
- 组件间按复杂度递增排列（简单模式在前，自治模式在后）。

## 六、生态格局
- 表格：项目 / 厂商 | 一句话定位 | 类型 | 成熟度 / 采纳数据（带日期锚点）。

## 七、对比评估
- 对比表（横向维度 ≤ 7），每维度给判断。
- 结尾决策建议：什么约束选 A，什么约束选 B。

## 八、实践：上手与最佳实践
- 最小上手路径（安装/配置/验证，给真实命令）。
- 最佳实践 3-5 条，每条可执行。
- 修正写回原则：发现错误要沉淀回资产本身，不只是一次性修补。

## 九、失败模式与坑（独立成章）
- 至少 3 条：怎么发现、怎么绕。安全 / 供应链风险必须有一条。

## 十、结论与下一步
- 一张总结表或 3 行要点收束全文。
- 给不同读者的下一步（开发者装什么 / 团队建什么 / 观望者盯什么指标）。

## 附录（长尾内容挪这里，不占正文）
- FAQ（3-5 个社区真问题）。
- 详细参数表 / 版本变更记录 / 扩展阅读。

## 参考资料
- 文末统一。一手（官方文档/仓库/论文）与二手分开两段，每条带日期。

---

## 写作规则（v3）
1. 开篇必有路线图句 + 类比。
2. "何时不用"与"何时用"同权重，不许只写适用场景。
3. 组件拆解用统一微结构（图 / 何时用 / 示例），读者形成阅读预期。
4. 举例即定义：先贴真实完整实例，再讲抽象。
5. 每章首句给结论（倒金字塔）；章节标题断言式，通过 3 分钟扫读测试。
6. 数字三要素：数值 + 来源 + 日期。
7. 一个图一个观点；表格横向维度 ≤ 7。
8. 附录承载长尾，正文只保留主线。全文读完 ≤ 15 分钟。
