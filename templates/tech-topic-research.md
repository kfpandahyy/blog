# 技术点调研模板（对象：概念 / 协议 / 机制，如 Skill、MCP、Agent Harness）

> 用法：把每章标题下的引导问题当成检查清单，逐章填。填不出来的章节，说明调研还没到位，回去补料，不要硬写。

## 文章标题
`《XXX 调研：一句话结论》`——结论前置，读者 10 秒知道立场。

## 一、问题背景
- 这个技术解决什么痛点？痛点不解决会怎样？
- 为什么是现在出现？前置条件（模型能力、生态、标准、成本）哪条成熟了？
- 一句话价值主张。

## 二、定义与边界
- 一句话定义（自己写的，不抄官方）。
- 不是什么：和相邻概念的辨析（如 Skill vs Tool vs MCP vs Plugin）。
- 边界：适用范围，超出后会失效的场景。

## 三、演进脉络
- 前身是什么？从哪个技术/产品演化而来？
- 关键时间节点：首次提出、重要版本、被哪家大厂采纳。
- 推动者：标准组织 / 开源社区 / 云厂商，各自动机。

## 四、架构与原理（心脏章节，篇幅占比 ≥ 30%）
- 分层拆解：画一张结构图。
- 核心机制：协议流程 / 关键数据结构 / 状态机，逐个讲。
- 关键设计决策：为什么这样设计而不是那样（至少讲 3 个决策及其理由）。

## 五、生态格局
- 实现方分类：官方参考实现 / 云厂商 / 开源社区 / 创业公司。
- 每类举代表项目，一行一个（项目名 + 一句话定位 + 链接）。

## 六、对比评估
- 至少两家/两条路线的对比表格。
- 每个维度给出判断，不只罗列。
- 明确各自的适用条件。

## 七、场景与实践
- 真实落地场景（按用户角色分：开发 / 运维 / 产品）。
- 上手成本：安装、配置、依赖。
- 典型案例 + 已知的坑。

## 八、趋势与启示
- 未来 1-2 年的走向判断（给依据，不给玄学）。
- 对数据库 / Agent 产品工作的关联：能借鉴什么、该警惕什么。

## 参考资料
- 统一放文末，每条注明标题、日期、链接。
- 一手资料（官方文档/仓库/论文）优先，二手解读标注来源。

---

## 写作规则（所有调研文章通用）
1. 参考资料只放文末，正文用"据官方文档"等字样指向。
2. 名词首次出现给全称 + 英文原名。
3. 数据、日期、版本号必须带来源。
4. 对比用表格，流程用图，陈述用短句。
5. 每章结尾一句判断，不堆事实。
6. 全文读完控制在 15 分钟内。
