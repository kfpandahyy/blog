# 技术点调研模板 v2（对象：概念 / 协议 / 机制，如 Skill、MCP、Agent Harness）

> 适用：调研一个技术概念，回答"它是什么、怎么工作、值不值得投入"。
> v2 变更（对照业界标杆文章）：TL;DR 框、标题断言化、最小实例先行、失败模式独立成章、FAQ 可选章、趋势要求可证伪、全文可扫读测试。

## 标题
断言式，不用名词短语。公式：`《XXX 调研：一句可争论的判断》`。
✅ "Agent Skill 调研：给大模型装'程序性知识'的开放格式"
❌ "Agent Skill 技术调研报告"

## TL;DR（正文前，3 句话以内）
1. 它是什么（一句）。
2. 为什么此刻重要（一句，给日期锚点）。
3. 读者现在该做什么（一句：采用 / 观望 / 深挖哪个点）。

## 一、问题背景
- 用一个"张力"开头：旧做法的真实痛点场景（谁在什么情况下被什么卡住）。
- 为什么现在出现：列前置条件，说清楚是哪条成熟了（模型能力 / 生态 / 标准 / 成本）。
- 章首第一句先给本章结论，细节后置（倒金字塔，以下每章同）。

## 二、定义与边界
- **举例即定义**：先贴一个最小真实实例（完整文件内容 / 命令 / 配置），再抽象定义。业界标准做法，不描述例子。
- 与相邻概念的辨析表（vs Tool、vs MCP、vs Plugin 这类）。
- 边界：什么场景不该用它。

## 三、演进脉络
- 画时间线（ASCII 或 mermaid）：关键节点 + 日期 + 推动者。
- 每个节点回答"为什么发生"，不只"发生了什么"。
- 点出路径选择：当时存在哪些备选路线，为什么胜出的是这条。

## 四、架构与原理（心脏章节，篇幅 ≥ 30%）
- 一张架构图 / 流程图。
- 核心机制逐个讲：协议流程、关键数据结构、状态机。
- 至少拆 3 个关键设计决策：为什么这样而不是那样。
- 给最小可运行示例（一段能跑通的真实内容），让读者可以动手复现。

## 五、生态格局
- 表格化：项目 / 厂商 | 一句话定位 | 类型 | 成熟度 / 采纳数据。
- 分类呈现：官方 / 模型厂商 / IDE / 框架 / 平台。
- 给数据时带日期锚点（"截至 2026-06，官方清单 40+ 产品"）。

## 六、对比评估
- 对比表（横向维度 ≤ 7），每个维度给判断，不罗列。
- 明确各路线适用条件。
- 结尾给决策建议：什么情况下选 A，什么情况下选 B。

## 七、场景与实践
- 按用户角色列场景（开发 / 运维 / 产品），每场景一句"上手成本 + 预期收益"。
- 最佳实践 3-5 条，每条可执行。

## 八、失败模式与坑（独立成章，业界文章的诚实度所在）
- 至少 3 条：触发失败、性能陷阱、安全 / 供应链风险、迁移成本。
- 每条给"怎么发现"和"怎么绕"。

## 九、趋势与启示
- 给 2-3 个**可证伪**的判断：12-24 个月内能被验证 / 证伪的预测，附依据。
- 不写玄学（"未来大有可为"这类句子删除）。
- 关联读者自身工作：能借鉴什么、该警惕什么。

## 可选：FAQ（3-5 个高频疑问）
- 从搜索联想、社区讨论里挑真问题，不自编。

## 参考资料
- 统一文末。一手（官方文档 / 仓库 / 论文）与二手（解读 / 媒体）分开两段列。
- 每条：标题｜日期｜链接。

---

## 写作规则（通用，v2）
1. **标题即判断**：章节标题写成断言句，读者只读所有标题能在 3 分钟内复述全文主线（3 分钟扫读测试）。
2. **倒金字塔**：每章首句给结论，细节和论据后置。
3. **例子先于描述**：贴真实内容（文件全文、命令、配置），不写"比如我们可以这样"。
4. **一图一观点**：每张图 / 表只服务一个论点；表格横向维度 ≤ 7，超了就拆。
5. **数字三要素**：数值 + 来源 + 日期，缺一不发。
6. **限制与坑独立成章**，不埋在正文深处。坦诚是技术文章的可信度来源。
7. 名词首次出现给全称 + 英文原名。
8. 全文读完 ≤ 15 分钟；超了就砍场景章和 FAQ，心脏章节（原理）不砍。
